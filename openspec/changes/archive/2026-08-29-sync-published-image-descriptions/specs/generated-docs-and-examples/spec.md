## MODIFIED Requirements

### Requirement: Docs and examples are regenerated from the version manifest and never drift

`mise run docs` SHALL regenerate `readme.md` and `examples/{github-actions,
gitlab-ci,gitea-actions,forgejo-actions}.yml` from `config/version.json` and
`config/images.json`, and CI SHALL fail when any committed output differs from a
fresh regeneration. The drift check SHALL be triggered by a change to either
manifest, so that an image-set change cannot land without regenerating the docs
it affects.

The experience context is the maintainer cutting a Flutter release and the reader
viewing the README/Docker Hub page: the maintainer never hand-edits versions in
the docs, and the reader never sees a version that disagrees with what the image
actually ships.

#### Scenario: An image-set change triggers the drift check

- **GIVEN** a pull request that modifies `config/images.json` and no other manifest
- **WHEN** CI runs
- **THEN** the docs drift check runs
- **AND** it fails if the committed `readme.md` differs from a fresh regeneration

#### Scenario: Committed output matches a fresh regeneration

- **GIVEN** a pull request that modifies either manifest or the generator
- **WHEN** the drift check regenerates the docs and examples
- **THEN** the committed outputs are byte-identical to the regenerated ones
- **AND** CI fails otherwise, naming the drifted file

### Requirement: README presents exact predownloaded versions and ready-to-use examples

`readme.md` SHALL be code-generated by `docs/build.mjs` from `config/version.json`
and `config/images.json`, and SHALL cover **every image in the published image
set**, deriving that set from the manifest rather than naming images in the
requirement. The README SHALL be structured as a quick-start: a one-line
description and a copy-paste usage snippet SHALL appear above the fold, before any
reference or contributor material. The README SHALL state the manifest Flutter
version in prose (not only in a badge). For each image the README SHALL render a
Running Containers registry table and a usage snippet whose image tag equals the
manifest Flutter version; the `flutter-windows` snippet SHALL use
`runs-on: windows-2025` (Windows containers cannot run under the Linux
`container:` pattern). The README SHALL name all four supported CI platforms
(GitHub Actions, GitLab CI, Gitea, Forgejo) and link to the `examples/`
directory. The README SHALL NOT include a generated table of contents, per-image
main-tool tables, a Roadmap section, inline Building Locally instructions, or an
inline FAQ; Building Locally SHALL live in `docs/contributing.md` and the FAQ
SHALL live in `docs/faq.md`, linked from the README.

The experience context is a CI engineer reading only the README who identifies an
image and copies a working usage snippet in seconds, and a Windows user who finds
`flutter-windows` presented as a first-class platform — without the README
drifting from the manifest. Naming the images in the requirement itself is what
let this drift: the requirement listed three images while the generator produced
four.

#### Scenario: Every image in the set is presented from the manifest

- **WHEN** `readme.md` is generated
- **THEN** it contains a section for every image declared in `config/images.json`
- **AND** the manifest Flutter version appears in the README prose

#### Scenario: Usage snippets use the current tag

- **WHEN** `readme.md` is generated for manifest Flutter version `X.Y.Z`
- **THEN** every image's usage snippet references its image at tag `X.Y.Z`
- **AND** the flutter-windows snippet uses `runs-on: windows-2025`

#### Scenario: Quick-start is above the fold

- **WHEN** a reader views `readme.md`
- **THEN** a one-line description and a copy-paste usage snippet appear before any
  Building Locally, FAQ, or contributor content

Note on the clause dropped from the first requirement above: it previously ended
"The generated `readme.md` SHALL be the file used both as the GitHub repository
README and as the Docker Hub repository description." That sentence made a
*publication* rule a clause inside a *docs-generation* requirement, because
publication had no spec of its own — which repositories receive a description,
when the sync runs relative to the release jobs, and what short description each
image gets are all concerns this capability cannot express. It now lives in the
`docker-hub-description-sync` capability as a requirement in its own right. No
behavior is lost: the generated `readme.md` remains the file pushed as each
image's full description.
